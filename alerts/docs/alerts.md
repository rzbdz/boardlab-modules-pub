# 通知

板子上发生了一件要人知道的事：复位失败了、板子在等有人按键、老化跑测试匹配到了那一行、关注的板子空下来了。这些事都走同一条路——**通知总线**：先记下来，再按每个**渠道**的规则推出去。

记下来这一件事永远会做，不管有没有渠道：页面右上角的铃铛、「通知」页能看到最近的，命令行 `boardlab alerts` 也一样。渠道决定的是**推到哪里**，比如推到一个飞书群，这样人不在电脑前、不在实验室里也能收到。

## 渠道

一个渠道是一个收消息的地方：

| 类型 | 是什么 | 怎么配 |
|---|---|---|
| `browser` | 页面自己弹的系统通知 | 配一条 `kind: browser` 的渠道；页面开着才收得到 |
| `feishu` | 飞书群的机器人 webhook | 群设置里加一个机器人，拿它的 webhook 地址，用命令行加进来 |

飞书的 webhook 地址是一个凭据：谁拿到它就能往那个群发消息。所以它只在加渠道的时候写一次，存进 boardd 的状态数据库，接口再也不会原样给回来（只给 `https://open.feishu.cn/…a1b2…` 这样的掩码），也不会进仓库。

```sh
boardlab alerts channel add lab https://open.feishu.cn/open-apis/bot/v2/hook/<webhook> --title BOARDLAB告警群
boardlab alerts channel test lab          # 发一条测试消息：群里收到就配好了
boardlab alerts channel list              # 有哪些渠道、规则、上一次投递的结果
boardlab alerts channel disable lab       # 先关掉（放假、维护时）
```

加渠道、改渠道、删渠道只有人能操作，agent 不行——那些操作能往一个群里发任意消息。加渠道要在命令行里做（地址贴起来方便）；已有的渠道可以在「通知」页里改规则、发测试、开关、删掉。

## 群里看到的样子

飞书群里收到的是一张**卡片**，不是一段纯文本：抬头按类型上色（失败红、等人橙、老化蓝、空闲绿），下面是这条通知的正文，再下面是板子、类型、时间、发起人，最后一行是哪个 boardd、哪个版本发的——一个群收几台机器的时候，一眼能认出是谁。

## 规则：一个渠道收哪些

没有规则就是全部。有规则时，一条通知要**同时**对得上某条规则的类型和标签才会推到这个渠道：

| 写法 | 收什么 |
|---|---|
| `--topic failed` | 只有失败（复位、刷机、启动、拿锁…） |
| `--topic failed,attention` | 失败，以及板子等人操作 |
| `--tag aging-1` | 只有带 `aging-1` 标签的（一次长跑、一块板子、一台主机） |
| `--topic aging --tag aging-1` | 这个老化测试匹配到的行 |

规则可以有好几条，任一条对上就收。「通知」页里可以直接改现有渠道的规则；加渠道用命令行。

## 类型

| topic | 什么时候 |
|---|---|
| `failed` | 一次操作失败了：复位、刷机、启动、拿锁。来自 boardd 的运行记录，不用谁去转发 |
| `attention` | 板子在等人做一件事（按 RESET、插线） |
| `aging` | 串口监控（[串口监控](console-watch.md)）匹配到了行，或者期待的行不来了 |
| `free` / `granted` / `stolen` | 关注的板子空闲了、排队轮到了、锁被抢了（页面自己发；推渠道也能用） |

## 主动发一条

```sh
boardlab alerts raise "产线 3 号台：板子冒烟了" --topic attention --board board-7 --body "先断电"
```

任何程序都能发：`POST /api/alerts`，body 是 `{topic, title, body, board, tags}`。老化脚本、外部流水线用它报自己的事，不用自己实现飞书。

## 它是怎么来的

通知总线是 `alerts` 模块：路由在 boardd 里跑，所以推渠道不依赖有人开着页面。别的模块不直接调飞书——它们 `inject: ['alerts']`，拿到 `lab.service('alerts').raise(...)`，剩下的由规则决定。想加一种新渠道（钉钉、Slack、邮件）就在这个模块里加一种 `kind`，别的地方不用动。
